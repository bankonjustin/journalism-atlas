## How "zero rendered change" was verified

Served the committed stop-1 tree and the working tree side by side and compared, on **58 pages at 1280px**:
1. **Every CSS rule, resolved.** For each rule (including `:hover`, `:focus`, `.active`, media queries) the computed text, background, border, outline, shadow, underline, fill, stroke and filter colors with `var()` resolved: **5,477 rules, 0 differences.** This covers states that never render at load.
2. **Every rendered element, at rest:** computed color, background, borders, outline, shadow, fill, stroke of **144,761 elements, 0 differences.**
3. **Negative control:** with `--color-lime` temporarily set to red the same check flagged 58 rule differences on three pages; reverted.
Not covered: colors set in JavaScript or in inline styles that only appear after a click, and mobile layouts. Neither was touched by this stop. A first attempt compared per-property rows and reported false differences (a `var()` shorthand stops listing its longhands); the check now compares whole-rule results.

**One real problem the check caught on its first run:** `partners/nj-lab.html` and `partners/njlab.html` link `variables.css` with a *relative* path (`assets/css/variables.css`), which resolves to `/partners/assets/css/…` and 404s, so those two pages never get the variables. My first pass moved their colors to `var()` and the check flagged it; I reverted and rebuilt the plan with a per-page browser test of whether the variables are really defined. Those two pages are now treated as "no variables.css" (below). Fixing the link is a one-line change per page (`/assets/css/variables.css`); it is a visible-change risk (it would turn on every `var(--color-…)` those pages already reference), so it is yours to approve.
